ステートレスな基盤と id-issuer
による管理体制が整ったため、次はシステム全体の整合性と堅牢性を高めるフェーズに
移行する。

今後の主要なタスクを、優先度順に整理した。

1. セッション認証の導入 (最優先)
   現在は id-issuer が ID を発行しているものの、Router
   は接続を無条件に受け入れている。
* タスク: Broker が Router に接続する際、id-issuer が発行した
  broker_session_id を提示し、Router が id-issuer
  に対してその有効性を検証する仕組み（認証）を実装する。
* 目的: 不正な Broker や期限切れセッションによる接続を排除する。

2. マーケット・ディスカバリーの実装
   現在、Broker は Market の ID を知っている前提でコマンドを打っている。
* タスク: BrokerClient が起動時（または要求時）に id-issuer の GET /markets
  を叩き、現在アクティブな市場一覧を取得・表示する機能を実装する。
* 目的: ユーザーが動的に追加された市場を認識し、注文を送れるようにする。

3. ルーター間連携（フォワーディング）の準備
   Router が複数台並列で動く構成（真のステートレス）を見据えた拡張。
* タスク: findSession でターゲットが自サーバにいない場合、id-issuer（または
  Redis）に問い合わせて「どの Router
  がそのセッションを保持しているか」を特定するロジックを実装する。
* 目的: 異なる Router に接続している Broker と Market
  の間でのメッセージ中継を可能にする。

4. FIX プロトコルの厳格化
   現在は基本メッセージの中継のみを行っている。
* タスク:
    * チェックサム・ボディ長エラーの処理: 不正な FIX メッセージに対する
      Reject(3) 送信。
    * ターゲット不在の通知: 注文の送信先が見つからない場合に、送信元へ
      Execution Report (REJECTED) を返す。
* 目的: プロトコルとしての正当性を担保し、エラー発生時の Broker
  側のハングアップを防ぐ。

5. コンフィグレーションの外部化
   URL やポート番号がハードコードされている箇所を整理する。
* タスク: application.properties や環境変数から、id-issuer の URL
  や待ち受けポート、Redis 接続情報を読み込むように各モジュールを修正。
* 目的: Docker や異なる環境（本番/開発）へのデプロイを容易にする。

  ---

おすすめの次の一歩:
「1. セッション認証の導入」を進めることで、id-issuer で発行した ID を Broker
-> Router -> id-issuer
と連携させて検証する、システムとしての「縦の疎通」を完成させるのが良いと考える
が、いかがだろうか。
